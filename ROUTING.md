# Как устроен routing

Routing связывает адрес страницы с тем, что приложение показывает пользователю. В этом проекте используется History API браузера и небольшой registry в `src/routes.ts`.

## Короткое объяснение для обсуждения проекта

«Маршруты описаны в одном registry: у каждого есть URL, название и тип страницы. Из этого же списка строятся меню и хлебные крошки, поэтому их не нужно поддерживать отдельно. При обычном клике приложение меняет URL через `history.pushState` и перерисовывает содержимое внутри общего shell. Кнопки “Назад” и “Вперёд” обрабатываются через `popstate`. После перехода фокус переносится на заголовок страницы; на мобильном сначала закрывается Offcanvas».

## Конкретный пример

1. Пользователь нажимает «Личные данные»: это настоящая ссылка с `href="/dashboard/profile"` и атрибутом `data-route`.
2. Обработчик обычного клика вызывает `preventDefault()`, чтобы браузер не загружал документ заново. Ctrl/Cmd-click и другие модифицированные клики сохраняют стандартное поведение ссылки.
3. `navigate('/dashboard/profile')` добавляет адрес в историю через `history.pushState`.
4. `renderPage()` читает `location.pathname` и передаёт его в `resolveRoute()`.
5. Registry возвращает запись с `page: 'profile'`; приложение показывает форму профиля, обновляет меню, крошки и `document.title`.
6. `focusTitle()` переводит клавиатурный фокус на H1. Заголовок имеет `tabindex="-1"`: его можно сфокусировать программно, но он не добавляется в обычную Tab-последовательность.

`pushState` сам не вызывает `popstate`, поэтому при программном переходе render вызывается явно. `popstate` нужен для перемещения по истории браузера.

## Что означают поля registry

| Поле | Назначение |
| --- | --- |
| `path` | Адрес, по которому определяется маршрут |
| `label` | Название для меню, крошек и заголовка |
| `page` | Какую страницу нужно отрисовать |
| `symbol` | Символ пункта меню |
| `menu` | Показывать ли маршрут отдельным пунктом sidebar |
| `parent` | Родитель маршрута для крошек и активного меню |

## Частые вопросы

**Почему без router-библиотеки?** Для шести фиксированных маршрутов достаточно небольшого слоя над History API. Для параметров URL, вложенных layouts, guards и более сложной навигации имеет смысл выбрать готовый router.

**Как работают два адреса обзора?** `/dashboard` и `/dashboard/overview` имеют одинаковое `page: 'overview'`. Оба используют `overviewMarkup()`. URL остаётся тем, который открыл пользователь; redirect отсутствует.

**Как определяется активный пункт?** По совпадению `path`, общего типа `page` или `parent`. Поэтому обзор активен для обоих его URL, а пункт личных данных остаётся активным на профессиональном подпрофиле.

**Что происходит на неизвестном URL?** `resolveRoute()` возвращает `undefined`, и приложение показывает собственную страницу «Страница не найдена».

**Почему форма не теряет черновик при переходе?** `draft` хранится в памяти модуля, отдельно от DOM страницы. При повторной отрисовке поля заполняются из него. После полной перезагрузки состояние сбрасывается.

**Что нужно для production-хостинга?** Сервер должен отдавать `index.html` при прямом открытии известного SPA-маршрута, например `/dashboard/profile`. Иначе сервер может вернуть 404 раньше, чем запустится JavaScript. Для файлов assets и API такая подстановка должна быть настроена отдельно и не скрывать реальные ошибки.

**Это уже routing заказчика?** Это standalone-реализация. Для интеграции потребуется сверить registry и компоненты с его репозиторием.

- `src/main.ts`: обработчик ссылок, `navigate`, `popstate`, `renderPage`, управление фокусом и Offcanvas.
